# QQ 音乐听歌伴侣（本地采集 + 云端查询 + 一起听）

一句话：电脑上的采集器在后台盯着 QQ 音乐，**整首听完**才记一条，传到云端；手机上的 Aru 通过 MCP 随时问云端"我刚在听什么、这周听了几遍"。

想更近一步的时候，还能让 AI**听一下你正在放的这首歌**——录音在你电脑上分析，只把文字报告传上去。

不需要开着 Aru，也不需要和 AI 对话，采集器自己会记。

> **代码作者**：本项目的代码由 DeepSeek Harness 中的 DeepSeek 模型（deepseek-flash）编写。
> 需求提出、验收和部署由项目所有者完成。
> 音频分析部分收录了开源项目**听骨（Tinggu）**的源码，出处和协议见 [CREDITS.md](CREDITS.md)。

## 一、文件夹里各是什么

```
qqmusic-companion\
├─ 启动听歌采集.bat      ← 日常双击这个（后台运行，不弹窗）
├─ 停止听歌采集.bat      ← 要停就双击这个
├─ 自检（出问题先点这个）.bat  ← 怀疑没记上，先点它看结果
├─ 安装音频分析.bat      ← 只有要"一起听"才需要跑一次（装几 GB 环境）
│
├─ local\                ← 【本地采集器】跑在你这台电脑上
│   ├─ collector.py      主程序
│   ├─ config.ini        ← 你唯一需要改的文件（填云端地址）
│   ├─ audio\            ← 一起听：录音缓冲、领任务、调听骨分析
│   ├─ vendor\           读取 Windows 播放信息用的库（已装好，别删）
│   └─ ...
│
├─ cloud\                ← 【云端服务】部署到服务器（Coolify）
│   ├─ app\              上传接口 + 7 个 MCP 工具
│   ├─ Dockerfile
│   ├─ docker-compose.yml
│   └─ .env.example      要填的口令（已生成好）
│
├─ vendor\tinggu\        ← 听骨（Tinggu）源码，MIT，音频分析靠它
│
├─ local-data\           ← 你的数据，和代码分开放
│   ├─ queue.db          还没传上去的记录（传成功就删）
│   ├─ logs\             运行日志，每天一个，自动只留 7 天
│   └─ collector.pid     正在运行的进程号（停止脚本用）
│
├─ tools\                ← 排查/安装脚本（读播放信息、重装依赖）
```

## 二、第一次使用（只做一次）

1. 云端部署好之后，会得到一个网址，例如 `https://xxxx.sslip.io`。
2. 用记事本打开 `local\config.ini`，在 `base_url =` 后面填这个网址（**不要带 `/mcp`**）。
3. 确认 `collector_token` 和云端环境变量 `COLLECTOR_TOKEN` 是同一串（真实口令在 `cloud\.env.local`）。
4. 保存。

> 从 GitHub 重新下载代码时，`config.ini` 不会跟着来（含口令，故意不提交）。
> 复制一份 `local\config.example.ini` 改名成 `config.ini`，再填上面两项即可。

### 万一本地代码丢了，怎么从仓库恢复

1. 下载仓库（GitHub 上 Code → Download ZIP，或 `git clone`）。
2. 装本地依赖：在项目目录运行 `python tools\fetch_wheels.py`（会下载读取播放信息用的库到 `local\vendor`）。
3. 复制 `local\config.example.ini` → `local\config.ini`，填云端地址和采集口令。
4. 双击 **启动听歌采集.bat**。

云端那边不用重装，在管理面板里点一次重新部署就能拉起来（数据在 `/data` 卷里）。

## 三、日常使用

- 双击 **启动听歌采集.bat**。没有窗口，只在后台跑。
- 正常听歌就行。整首听完的歌会自动上传；听一半切走的不算、不传。
- 要用的时候，在 Aru 里问 AI，例如"我现在在听什么"、"这周一共听了几首歌"。
- 想停：双击 **停止听歌采集.bat**。

电脑重启后不会自己启动（按你的要求），需要再双击一次。

### 一起听：让 AI"亲耳"听一下这首歌

除了知道他放了什么，还能让他**听一下**——分析你正在放的这首歌，拿到一份文字听感报告。

**怎么用**：在 Aru 里说"你听一下这首歌"，AI 会按顺序用到三个工具：

| 工具 | 用途 |
|---|---|
| `listen_now(mode, wait_seconds, when_finished)` | 发起"听一下"。`mode` 选 `shallow`（浅听）或 `deep`（深听）；`when_finished=true` 是**预约**：不现在分析，等这首自然放完再用完整录音深听 |
| `get_listen_result(job_id)` | 按任务号取那一次的报告（发起时没分析完，或者事后回看，都用它） |
| `get_listen_history(days, title, limit, offset)` | 先看"什么时候听过哪些歌"的清单，**一次只看一首**，挑中哪首再取详情 |

清单只给时间、歌名、浅听/深听、成功与否和任务号，不带报告正文；七天里可能有很多首，用 `limit`/`offset` 翻页，返回里的 `total` 是总条数。想回看哪一首，就拿它的任务号调 `get_listen_result`。

**两档的区别**（实测）：

| 档位 | 要等多久 | 能听到什么 |
|---|---|---|
| 浅听 `shallow` | 约 1 分钟（录 45 秒就够） | 速度、亮度、编曲时间轴（谁先进来）、能量走向、注意力峰 |
| 深听 `deep` | 歌放完后再等 1~2 分钟 | 上面全部 + 六轨分离（鼓/贝斯/吉他/钢琴各轨起止）、嗓音质感、和弦与调性、张力曲线 |

**前置条件**：电脑开着、采集器在跑、并且**正在放歌**。不满足会直接告诉你原因，不会假装听得到。

**录音规则**（这是和需求方商量定的）：

- 只保留**当前这一首**，切歌立刻清空重录，不会把两首歌接在一起
- 单首最多存 10 分钟，超了从最前面丢
- 录到的音频**只存在本机临时目录，分析完立刻删除**
- **上传的只有文字报告**，音频不出电脑

**预约式深听**（`listen_now(when_finished=true)`）：

- 适合"这首还在放，但我想等它放完再听完整的"。
- 云端记一条预约，**不立刻分析**；采集器发现这首自然放完（切到下一首）时，用**刚放完那首的完整录音**跑深听。
- 为了做到这点，切歌时录音进程会把刚放完那首挪到 `local-data\audio-tmp\last\`，**只留最近一首**，分析完或下一首放完即删。
- 预约太久没等到（比如这首一直没放完）3 小时后自动作废。
**关于"听到的其实是片段"**（很重要）：

- 你点"听一下"的时候，手上只有**从采集器开始录到那一刻**的声音：可能是完整一首，也可能是刚放的 40 秒，甚至是从副歌开始的半首。
- 听骨拿到多少就分析多少，它**不会自己知道缺了前面**。所以报告最前面会加一行 **【完整度】**：
  - `基本是整首（录到 200 秒，全曲约 204 秒）`
  - `这次只录到 42 秒，全曲约 204 秒（21%），是片段，不是整首；时间从录音起点算，起点在歌里的位置无法确定（QQ 音乐不报进度）`
- **深听要求覆盖率 ≥ 85%**，不够就直接拒绝并说明原因，不会硬出一份"看着像整首"的深听。
**它内部是怎么跑的**（维护时要知道）：

```
采集器（collector.py）
 ├─ 主循环：读 QQ 音乐状态、判整首听完、上传记录
 ├─ 每秒把"当前在放什么"写进 local-data\audio-tmp\state.json
 └─ 启动时拉起两个独立进程：
      ├─ audio\recorder_proc.py  只负责录音，按 0.5 秒一块写成文件
      └─ audio\agent.py          领任务、拼 wav、调听骨、回传报告
```

**为什么拆三个进程**：录音驱动（soundcard/cffi）在录音时几乎一直占着 Python 的全局锁，
放在同一个进程里会把上传线程和任务线程饿死（实测：开启录音后所有上传都超时）。
拆开之后互不影响，这是踩过的坑，改架构时别合回去。
**第一次用要先装环境**（只装一次）：

1. 双击 **安装音频分析.bat**
2. 会建一个独立环境在 `C:\Users\<你的用户名>\AppData\Local\qqmusic-audio\`（**不放项目文件夹**，约 5~6 GB）
3. 其中 PyTorch 的 CUDA 版约 2.6 GB，是最慢的一步
4. 首次深听会再自动下模型：PANNs 约 330 MB（乐器识别）、Demucs 约 80 MB（六轨分离）
5. 装完不用再管，以后双击"启动听歌采集.bat"就会带上录音和分析

> 没有显卡也能跑，只是深听会慢很多（CPU 上每首 3~5 分钟）；有 NVIDIA 显卡会快一个量级。

## 四、数据在哪、会不会外泄

- 本地：`local-data\queue.db`（没传出去的记录）和 `logs\`。
- 云端：`/data/qqmusic.db`（七天记录），超出七天自动删。
- 上传走 https，带口令；MCP 查询也要口令。没有别的遥测。
- 不保存音频，也不保存歌词正文。
- 一起听的录音**不落地长期保存**，分析完即删；云端只存文字报告（和播放记录一样保留七天，过期自动删）。

## 五、出问题了怎么办

先双击 **自检（出问题先点这个）.bat**，它会把"能不能读到 QQ 音乐、能不能连上云端"打印出来。

| 现象 | 先看这里 |
|---|---|
| 双击启动没反应 | `local-data\logs\collector.log` 最后几行 |
| 云端查不到当前状态 | 电脑是否开机、采集器是否在跑、自检里云端连通性 |
| 一直显示"数据可能过期" | 采集器没在跑，或者电脑睡眠了 |
| 某些歌一直不记录 | 这些歌查不到时长（会在"服务状态"里显示漏了几首） |

日志可以直接用记事本打开。

## 六、已经知道的限制（不是 bug）

1. **进度是算出来的**：QQ 音乐不把播放进度交给 Windows（实测恒为 0），所以进度 = 累计播放时间，误差 1~2 秒，返回值里 `position_estimated: true`。
2. **整首听完才记**：按你定的 95% 判定；暂停后不继续的不算。
3. **查不到时长的歌不记**：比如冷门曲、现场版；会在服务状态里累计"因时长未知漏记"数量。
4. **服务重启时正在放的那首**可能不计入（从 0 开始计时）。
5. 只支持 Windows 桌面版 QQ 音乐；手机端、iOS 不采集。
6. 电脑关机期间没有新数据，云端只能查已上传的历史（会明确标注最后更新时间）。

一起听还有几条：

7. **只能听"采集器开着之后"放过的歌**：还没开始录音的那段补不回来；所以想让他听，采集器得先开着。
8. **深听吃资源**：跑的那一两分钟 CPU/显存会满，跑完就释放。
9. **没有 basic-pitch**：音符层装不上（它要求和现有库冲突的旧版 numpy），所以"旋律音符"这层不出；听骨自己也说这层只有两三成准。
9.1 **"乐器出没 / 环境声"这一层现在默认是关的（已知现状，不是装坏了）**：它需要两个 PANNs 模型（`Cnn14_mAP=0.431.pth`、`Cnn14_DecisionLevelMax_mAP=0.385.pth`，各约 312MB），唯一官方源 Zenodo 在国内很慢、还限速，实测下到 200MB 左右会卡住。
    - 没下全时，`local/audio/analyze.py` 会**自动跳过这一层**，报告里写"乐器针失灵"，其余分析（人声逐句、编曲时间轴、能量、调性、亮度）照常。
    - 两个模型放全（每个 >300MB 且能正常读取）就会自动启用，不用改代码。
    - 文件位置：`C:\Users\<用户名>\panns_data\`。
    - 想要这层的话：网络好的时候重跑下载，或者把这两个文件手动放进去。
10. **纯音乐会按纯音乐处理**：有人声的歌如果配不到歌词，可能被当成纯音乐，声线那几层就不出。
11. 报告是**素材，不是答案**：听骨的报告开头有一段"共听礼仪"，就是提醒读报告的 AI 别复述数字、别替人下结论。
